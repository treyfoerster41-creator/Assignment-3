## What I built

I kept paced breathing as the main experience: six four-second inhales and six six-second exhales, for 60 seconds of active practice. The second course skill is 5-4-3-2-1 sensory grounding, with five prompts that advance every 15 seconds. I added three short, app-authored choices: visual anchor, sound noticing, and support points, each with three fixed prompts at 15 seconds apiece. These three additions are prototype content; I do not claim they came from the assignment's study or that they have been evaluated. Each exercise starts with one action and continues hands free. A person can pause, end, or open Crisis support while practicing. Optional spoken cues are off by default, use browser speech synthesis, and do not use a microphone; visual prompts stay on screen.

I added a separate Profile page. A profile is a local label, not a sign-in or cloud account. It can save a person's most recently chosen practice, recommendations from their conversation, and links to their local practice and conversation history. Starting a practice updates the saved preference; simply receiving a suggestion does not. The user can choose another practice, switch profiles, delete a profile, or clear history. I do not send the profile display name to Gemini.

I connected the optional chat flow to a backend Gemini REST adapter. The server sends the current fictional message, a short recent conversation, and a small amount of profile activity context. It asks for a brief reply and one exercise ID from the five fixed choices. The server validates the result and saves a recommendation only when the ID is allowed. The model cannot create exercise steps, change timing, start a practice, write to SQLite, select a screen, or control Crisis support. The user decides whether to try the suggestion.

I revised the chat after trying a greeting. It shows the recent exchange, answers a greeting conversationally, and asks an optional question instead of treating “hi” as a complete check-in. The prompt tells Gemini to keep a stated goal in view if the conversation briefly wanders, then point gently to the separate suggestion card shown right below the latest response. For example, after a fictional student says they want to de-stress and then talks about a game, the local demo rules carry the goal forward and select a fixed visual-anchor option. The user can try the suggestion, choose another practice, or skip it. In no-key demo mode, the local rules and preset reply are labeled as demo behavior, not Gemini.

When I reviewed the chat again, I noticed that a generated reply could say it was “starting” a practice even though chat cannot start one. I tightened the model instructions and added a server-side check that replaces replies claiming to start a practice or suggesting free-text activities. The model can return only one of the five fixed exercise IDs, and the app displays it as a separate suggestion. Chat never creates a practice session; the user must choose a practice button to start. I also changed live-provider failure handling: local rules may offer one fixed option based on the fictional conversation and allowed activity context. The response and card state that Gemini was unavailable and that the option came from local rules. This fallback is separate from a live Gemini recommendation. I tested the fallback with mocked replies. My later direct Gemini check returned HTTP 429, so it did not produce a live reply or test the updated fallback in the browser.

I changed the reduced-motion option so the breathing ball stays one size for the whole exercise. I also made the optional spoken breathing cues a little warmer and more encouraging. Browser speech uses the voices available on the device, so its sound can differ; I have not confirmed audibility in the student's target browser. Voice remains off unless the user turns it on.

I added my Gemini key to the ignored project-root `.env`; I did not put it in the repository, report, or chat. My first model choice, Gemini 3.8 Flash, returned HTTP 503 even after one bounded retry. I changed the configured model to Gemini 3.6 Flash, which returned a response, but the initial 160-token limit cut it off before the JSON reply was complete. I raised the limit to 512 and added a guard so truncated output cannot become a suggestion. A fresh fictional backend request then returned a complete response and the fixed breathing exercise ID. I also sent a fictional classroom example through the browser; Gemini returned a conversational reply and the app suggested the fixed grounding exercise. No profile was selected for that browser check, so the suggestion was not saved to a profile. The app now labels the model separately from provider health and saves no recommendation after provider failure or invalid output.

The app describes itself as a local coursework prototype for fictional classroom scenarios. It does not claim to be a therapist, provide a diagnosis, or monitor anyone. The Crisis support panel remains available without the API or model. A small phrase rule can open it, but that rule is limited routing, not a distress detector, and it can miss or overmatch wording.

## How the design uses the research

I used the supplied R1 finding to keep the breathing sequence around one minute. I used R2 and D4 to keep Crisis support visible on every screen and independent of Gemini. R3 and R4 shaped the pause/end controls and the rule that a recommendation never starts an exercise by itself. D2 and D3 shaped the one-prompt-at-a-time flow and the choice to make writing optional. D5 informed the lightweight profile history: it uses selected practices and recommendations without asking the user to configure a large profile. D6 informed the plain, low-stimulus wording and optional motion/speech controls.

I did not implement a distress detector. The supplied D1 finding says the study did not establish how a system could know that distress had risen or what it should contract. The app only uses the person's explicit fictional message and saved exercise choices.

## How I evaluated it

I ran the backend suite with temporary SQLite databases and mocked model/provider behavior. All 33 unittest cases passed. Eighteen cases send distinct fictional messages through the app's deterministic mock recommendation path and confirm that the expected fixed exercise ID is saved to the selected profile. Other cases cover the five scripts, preserved database rows during migration, goal carryover through a side topic, and a Gemini-failure fallback saved with its correct source label. Two API cases feed in mocked replies that claim to start a practice or suggest an invented activity; the app replaces those replies with fixed boundary text and creates no practice session. The [scenario matrix](evidence/assignment-3-part-3-scenarios.md) lists all eighteen scenario results. These checks evaluate my app's local mock, validation, and persistence behavior; the latest live request returned no model output.

I also checked three behavior invariants. First, an exercise suggestion does not start a practice until the user chooses it, and an invented exercise ID is rejected. Second, a matched fictional crisis phrase bypasses the model and the triggering text is not stored. Third, the backend requires the fixed duration and all steps/cycles before recording a practice as complete. The test suite also checked profile history, deleting a profile, history clearing, migration from the earlier database schema, a mocked Gemini request with a five-ID JSON schema, and sanitized failure behavior.

My unexpected result came from the first version of the scenario test. I reused one profile, so a vague “short exercise” message followed the previous grounding recommendation. That was the app using profile history as designed, but it meant the test was not isolating the message itself. I changed the test to use separate fictional profiles and added a separate check for a vague follow-up that should use prior profile activity. This is a software-testing observation, not a finding about users or clinical outcomes.

One limitation I have not tested or fully resolved is how the grounding flow works for someone who cannot or does not want to use a particular sense, especially smell or taste. I added wording that says the user can let a prompt pass, but there is no alternate sense prompt or skip button. I have not completed a formal accessibility review or run a user study. Browser speech has not been confirmed audible by me.

After I tried the five choices again, I found that only paced breathing worked. The backend names the prompt length `step_seconds`, but the frontend was using `stepSeconds` without mapping it. That made prompt counts and countdowns show `NaN` for grounding and the three app-authored options. I mapped the API field and kept a local timing fallback. In an isolated browser check using a temporary database, all four prompt-based practices showed the first prompt and a numeric countdown; Support points advanced automatically to its second prompt after 15 seconds. The fix did not write to my saved app history. I reran the backend tests and production build after the fix; all 33 tests and the build passed. I have not tested the reduced-motion ball or listened to the optional spoken cues in my target browser.

The eighteen scenario results and HTTPX transport test are mock evidence; they do not contact Google. An earlier browser chat returned a valid Gemini response, one later direct request returned HTTP 429, and my latest browser review found that live chat was working. These checks do not establish consistent provider availability or evaluate Gemini's overall quality. I will keep the key out of this report, repository, and recordings.
